- 2026-11-04 — Parser: one label-scan rule (first number after a label and before the next label, unit before or after) instead of per-layout regexes, because real output varies: one-line-per-nutrient, HTML tables with unit and value in separate cells, glued single-line blobs, and prose lines. A gram/mg value must carry a unit (a bare number is a calories or %DV column); an explicit kcal beats a kJ conversion; `verified` = panel parsed AND no cut-off flag, and the smoke test additionally requires the output not looped. The cut-off heuristic (`[…]`, trailing hyphen, unbalanced parenthesis) does NOT fire on the yogurt, whose ingredients are cut off but come back well-formed, so ingredients stay unverified text regardless.
- 2026-11-04 — First full OFF score (50 images, official prompt, non-streaming chat_completion): carbs 42% (21/50), fields 51% (179/350) against OFF, 1 looped output, ~$0.08 for the run (p50 3.4 s, 705 tokens in / 306 out). Not a model-quality number: of 171 wrong or missing fields, 96 have no trace of the OFF value in the OCR text (model misread, photo is not a nutrition label, or OFF is wrong) and 75 do. The main model-side finding is that tables with two-line labels (fat / of which saturates) come back as one merged row with a value dropped, shifting every row below by one. The parser assigns a value to the first of two merged labels and never to two labels. Multi-language EU blobs with 20+ languages are not handled (labels unknown).
- 2026-11-04 — `nutrients_verified` is only weakly predictive: field accuracy 58% (159/273) among verified images vs 26% (20/77) among the rest. It means "a panel was parsed, nothing cut off, no loop", not "the numbers are right". The UI must keep showing the source image next to the number.

- 2026-11-04 — API decided: non-streaming `chat_completion` (`ocr_chat`) is the primary and only path in the app; `document_extraction` cannot be created for this model (probe check 6, 400) and PDFs are rendered to images. Streaming stays available in `app/eis.py` for the UI's live request view.
- 2026-11-04 — Parser, round 2: decimal comma is always a decimal (`1,7` = 1.7, no thousands separator in nutrient values). Energy: kcal wins, kJ is stored in `energy_kj`, kJ-only is converted (/ 4.184) and flagged `energy_converted`; a unit glued after a number (`kJ2030kcal 492`) belongs to the next number, so the unit before the number wins when the two differ. Labels are matched case- and accent-insensitively (`fold`, Latin only, kana untouched); added Japanese saturated fat, Italian `valore energetico`, singular `matière grasse`, `うち`. A nutrient named in several languages in a row (`Hidratos de carbono / Carboidrati`) is one label run, so the "two labels, one value goes to the first" rule works across runs.
- 2026-11-04 — Column choice: the first `100 g` / `100 ml` header fixes the value column for every row (`ParseResult.column`, `.basis` = 100g | 100ml | serving | unknown); columns left of it are counted from serving/size headers, ignoring ones preceded by `%`. A row with no value in that column is skipped, never read from another column (a missing field beats a wrong one). A word-boundary bug (`Declaração` contains `ração`) briefly made this drop fields on two Iberian panels; fixed and covered by a test.
- 2026-11-04 — `parse_suspect` = parsed kcal differs from 4C+4P+9F by more than 20% (and by more than 5 kcal, so tiny values do not trip on rounding), or sugars > carbs, or saturates > fat. `nutrients_verified` now requires it to be clear. Known blind spots: fibre, polyols and alcohol make the kcal estimate low (drinks and sweeteners can be flagged wrongly), and a shift that swaps two similar-sized values (Nutella 3017620425035: carbs and protein taken from the neighbouring rows) keeps the kcal estimate within 20%, so it passes. On the 50 images: 4 panels suspect (field accuracy 25%) vs 46 not (55%); verified 63% (158/252) vs not verified 28% (27/98), up from 58% vs 26%.
- 2026-11-04 — Scoring: every wrong or missing field gets one cause, first match wins: unit, shift, comma, then (value in the text) column / synonym / shift by the label on its row, or (not in the text) truth_disagreement if >=3 parsed fields are all within 15% of OFF and >=2 are out of tolerance, else model. `model_read_accuracy` = the OFF value (comma/dot, trailing zeros, whole kcal or kJ equivalent) is in the raw OCR text; a zero counts as read only if a zero sits on a row of that nutrient. The old parser's rows are frozen in `reports/baseline/score_before.json` and re-classified with the same code, so `reports/score.md` shows before/after on the same cached OCR text.

- 2026-11-04 — Order-aware alignment (`_align` in `app/parse.py`): for EU-ordered panels (labels a subsequence of fat, saturates, carbs, sugars, fibre, protein, salt) the ordered labels are lined up with the ordered values of the per-100 column (an empty-label row and extra glued columns count as rows), every way of leaving out the surplus labels (or trailing values) is tried, and the winner has no rule broken (sat <= fat, sugars <= carbs, fibre <= carbs, no value over 100 g, Atwater within 20%), then the cheapest skip (the "of which" rows are free, macros cost 1), then the smallest Atwater error, then skips later labels. No valid alignment: the row scan stays and `parse_suspect` flags it. US-style panels (sodium, cholesterol) are never realigned. Needed two OCR repairs: a unit glued to a connector word (`0,1 gde las cuales`) is a unit, and `Glacides` is accepted as a carbs label (a typo seen on a real pack). Tests use barcodes 3017620425035 (lost sugars, rows shifted), 7622210449283 (saturates lost, sugars on the fibre row, salt on an unlabelled row) and 20005733 (a duplicated value row).

- 2026-11-05 — Column choice for HTML header rows (`app/parse.py`). Diagnosis of the table prompt's 26 `column` misses found four separate bugs, not one: (1) merged rows of k labels over W columns arrive as k*W stacked cell values (`7,0 g<br>1,3 g | 2,8 g<br>0,5 g`), now read column-major when the count is exactly k*W (a row with k labels and only W values stays "one value per column, first label gets it", the Nutella case); (2) a unit glued in front of the number (`g3,5`) is a unit unless it follows a letter (`Omega3`); a gram unit glued to a word but followed by a space (`Vetteng 47`) still works; (3) the header names the 100 g / 100 ml column and its size, and a header whose cell order contradicts the data's scale (header `250 ml | 100 ml` over `10.6 | 27`, ratio 2.5) is swapped (`column_swapped`; needs a clean row, a size on the other column, ratio within 20%); (4) the number of value columns is taken from the rows, not the header, when they disagree (a header naming `100 g` alone over rows with two values each is a two-column table). The header region now ends at the first nutrient label after a column marker, so a glued blob's own rows are not read as headers. `basis` and `column` are still recorded. Official 201 -> 205 correct fields (4 gained, 0 lost), table 204 -> 219 (15 gained, 0 lost). - 2026-11-05 — Allergen kinds. `allergen_mentions` is a nested field of `{name, kind}` (keyword, keyword), kind = `contains` or `may_contain`, one entry per allergen per capture (nested so a name keeps its own kind in filters and aggregations). A match is `may_contain` only if every occurrence sits in a clause started by a "may contain" phrase in en/fr/es/pt/de/it (also "traces of", "made in a facility that also processes"); the clause ends at the next full stop, semicolon or line break. Safety direction chosen on purpose: an allergen named both ways is `contains`, and a wrapped precaution line (clause cut by the line break) over-reports as `contains`, never the reverse. API: `allergen_kind=contains|may_contain` on `/api/search` and `/api/aggs`; the aggregation returns `{key, count, contains, may_contain}` per allergen. UI: Result shows two rows (Contains solid, May contain dashed), Library cards mark may-contain chips "may: ...", the facet shows both counts, plus a kind filter. Still labelled "as read"; still a keyword match (it cannot read negation such as "free from milk").
